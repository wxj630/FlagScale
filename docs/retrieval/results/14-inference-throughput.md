# 14 · 推理吞吐（多平台实测，含 Ascend 910C）

**这是"推理"口径，与 [07](07-a100.md)–[09](09-ppu.md) 的训练吞吐不是一回事。**
训练吞吐含反向传播与优化器，推理只含前向；两者相差 2-3 倍是正常的，
不该混在同一张表里比较。

## 一、口径（先看，否则数字没意义）

| 项 | 定义 |
|---|---|
| **测量范围** | **只计模型前向**。数据加载、tokenize 后的 CPU 侧排序全部在计时区间外 |
| **同步** | 每次前向前后各 `synchronize` 一次，否则测到的是 kernel 发射延迟而不是计算时间 |
| **单位** | embedding 任务 = **文本编码数/s**；reranker = **查询-文档对/s** |
| **batch** | BGE 32、CLIP 64、Reranker 4（reranker 受显存限制） |
| **样本量** | BGE 2,000 query × 16 候选 = 32,000 次编码；CLIP 5,000 图文对 = 10,000 次编码；Reranker 300 query × 16 = 4,800 对 |
| **实现** | `examples/retrieval/evaluate_retrieval.py` 的 `InferenceClock`（`1f7e9709` + `20a9242f`） |
| **原始产物** | `docs/retrieval/data/inference/*.json`（每份都含 `inference` 字段，可复核） |

> **为什么必须重新测，不能从旧结果反推**：历史 eval JSON 只有
> `model_type/task/checkpoint/split/samples/metrics`，**没有任何时间字段**；
> 文件 mtime 又混着模型加载和几百 MB 的 predictions 写盘，无法反推。

**PPU 的 reranker 推理是能测的** —— 之前的文档写"8B 单卡放不下、测不了"是**错的**。
实际跑通了全量 16,740 query。这是四个平台里唯一一对**全量口径完全可比**的数据
（A100 15.76 vs PPU 14.55），也是最可信的一组。

**PPU 的 reranker 推理是全部结果里最接近达标的**：实测系数下 162.3%、
验收方更严的 1.031 下仍有 **111.9%**。BGE 在 PPU 上只有 33.0%、
CLIP 是 103.3%，说明 PPU 的问题集中在 BGE 那种**小模型 + 反向传播**的场景，
8B 前向反而不是它的短板。

**⚠️ 300 档里 A100 不是最快的，原因值得说清。**

A100 80 GB 在这个 shape 上**吃不饱**：8B 模型、batch **4**、seq 640，
即 M≈2,560 的极小 GEMM，A100 的 312 TFLOP/s bf16 峰值用不上，
实际瓶颈在 kernel 发射与访存。昆仑芯/昇腾各自的内核在小 batch 下开销更低，
所以**反超 12-22%**。

**batch 4 是被显存逼出来的，A100 自己也放不大。** 实测 A100 用 batch 16
直接 OOM：

```
torch.OutOfMemoryError: Tried to allocate 41.51 GiB.
GPU 0 has a total capacity of 79.25 GiB of which 37.54 GiB is free.
```

batch 16 = 4 × 16 × 16 = 1,024 条序列 × 640 token、8B 参数，
激活 + KV 直接顶穿 80 GB。所以：

| 平台 | batch 4 能跑 | batch 16 能跑 | 原因 |
|---|---|---|---|
| A100 80 GB | ✅ | ❌ OOM | 激活 + KV 峰值 41.5 GiB |
| 昆仑芯 96 GB | ✅ | 未测 | — |
| 昇腾 64 GB | ✅ | ❌ 更不可能 | 显存更小 |
| PPU 96 GB | ✅（全量跑通）| 未测 | — |

**所以这张表的正确读法是："batch 4 是四个平台唯一都能跑的共同部署点，
在这个点上三家国产卡都不慢于 A100"**，而不是"国产卡算力超过 A100"。
这是**同一约束下的横向对照**，不是峰值算力排名。

### ⚠️ 测量必须在空闲卡上单独跑

2026-11-05 在 A100 上把 BGE（卡 0）和 CLIP（卡 1）并行启动，结果：

| 模型 | 并行测 | 单独测 | 差异 |
|---|---|---|---|
| BGE-M3 | 363.3 样本/s | **395.2** | −8% |
| CLIP | **100.3 样本/s** | **461.1** | **−78%** |

CLIP 差 4.6 倍。原因是 `InferenceClock` 只计模型前向，
但**图像解码/预处理发生在 CPU 上、且在计时区间之外**；
两个进程抢那台机器的 **26 个核**时，GPU 前向被 CPU 侧喂数据拖住，
同步等待的时间被算进了 `model_seconds`。

**所以：**
1. 一台机器上**一次只测一个模型**，或者至少分到不同物理机。
2. 看到明显低于同类的数字（如 CLIP 比昆仑芯低 3 倍），**先怀疑测量环境**，
   不要当成硬件结论。
3. 表里 A100 的值全部来自单独测量。

## 四、三个说明

**1. PPU 的 reranker 推理能测，之前的文档写错了。** 8B 模型在 PPU 96 GB 上
单卡跑得动，已实测全量 16,740 query（14.55 对/s）。旧文档写"单卡放不下、
报 `CachingDeviceAllocator: invalid device index`"——那次失败是环境问题
（容器卡号/软链），不是显存不够。**教训：把一次环境报错当成硬件上限写进结论，
会永久性地漏掉一个平台的数。**

**2. 昆仑芯 reranker 用的是 base 权重。** 训练已跑完 epoch 1 但 train/val 严重背离
（见 [08](../results/08-kunlunxin.md) §昆仑芯 reranker），那个 checkpoint
不构成可部署的模型，所以推理吞吐仍以 base 权重为准。

**3. 昇腾 910C 的推理吞吐也用 base 权重。** BGE/CLIP 是单卡、batch 32/64；
Reranker 是单卡 batch 4，4 卡训练吞吐不直接可比。
原始 JSON：`docs/retrieval/results/data/inference/ascend_{bge,clip,rr_base}.json`。
纯前向下 BGE 是昆仑芯的 96.5%、CLIP 是 121.8%、Reranker base 是 108.9%；
训练吞吐的差距主要来自反向/优化器和非 GEMM 小算子，不是前向算力。

**4. A100 reranker 有两个口径，别混用。**

| 用途 | 命令 | 吞吐 | 用于 |
|---|---|---|---|
| **跨平台对比** | `--max-samples 300` | **18.93 对/s** | §二 那张四平台表 |
| 全量评测 | 不设 `--max-samples`（16,740 query）| 15.76 对/s | A100 base vs trained 指标 |

全量那个数**不能**和昆仑芯/昇腾比：他们只测了 300 条。反过来，
300 条这个数**不能**用来说明评测要多久——全量约 4.7 小时。

## 五、复现命令

**跨平台对比必须用这一组参数**（`--max-samples 300 --batch-size 4`），
换任何一个数那张四平台表就不再可比。

```bash
# A100 / 昆仑芯（卡号按本机改）
python examples/retrieval/evaluate_retrieval.py \
  --model-type qwen3_reranker --task reranker \
  --model-path /flagos-retrieval-models/Qwen3-Reranker-8B/Qwen3-Reranker-8B \
  --data-path /flagos-retrieval-datasets/t2ranking/t2ranking/triplet-15 \
  --split test --max-samples 300 --num-negatives 15 --batch-size 4 \
  --device cuda --max-length 640 \
  --output data/inference/<platform>_rr_base.json
```

```bash
# BGE / CLIP（昆仑芯卡 2，单卡）
python examples/retrieval/evaluate_retrieval.py \
  --model-type bge_m3 --task embedding \
  --model-path /flagos-retrieval-models/bge-m3/bge-m3 \
  --data-path /flagos-retrieval-datasets/t2ranking/t2ranking/triplet-15 \
  --split test --max-samples 2000 --num-negatives 15 --batch-size 32 \
  --device cuda --max-length 512 \
  --output infer_bge.json
```

```bash
# PPU（容器 flagos-retrieval 内，需 GEMS_VENDOR=thead 与 NCCL_SOCKET_IFNAME=bond0）
export FLAGSCALE_DEVICE=flagos FS_PLATFORM=flagos FLAGSCALE_DISTRIBUTED_BACKEND=flagos
export FLAGSCALE_AUTOCAST_DEVICE=flagos GEMS_VENDOR=thead NCCL_SOCKET_IFNAME=bond0
python examples/retrieval/evaluate_retrieval.py ... --device flagos ...
```
